# devf Feed Engine — Prioritized Improvement Report

## 1. Overall verdict

**The engine is sophisticated and mature, not "fine."** This is a genuinely above-average recommender: 7 parallel fail-open candidate sources with panic isolation and a widening-window ladder, per-cohort logistic LTR with IPW position-bias correction, an online-trained two-tower with hash-trick priors, a Thompson-sampling strategy bandit, real-time trending with decay + anti-bot weighting, MMR with creator de-duplication, and a coherent mood/dopamine/anti-loop psychology layer. Most heuristic terms are individually clamped so nothing NaNs or capsizes. The design intent is consistently strong, and the per-user warm-once caching shows the team understands hot paths.

But it has real, fixable gaps that materially hurt ranking efficacy and will not survive the millions-of-users target:

- **One scale defect dominates everything else:** `getContentScore` is uncached and fires ~3 DB queries per call, ~150-250 times per feed request on the same ~100 rows — roughly 450-750 redundant Postgres round-trips per page. Its own docstring claims it caches. Found independently by 5 audit lanes; this is the single biggest blocker to scale.
- **Several "advanced" ML/psychology features are silently broken or dead in production** — they look impressive but don't do what they claim: the Platt calibrator has train/serve skew, the Bayesian uncertainty bonus is just fixed-variance noise, three composeFeed slot types have no buckets (whole strategies degrade to generic content), the learned mood-transition model is never written, the MMR lambda ramp is dead code, and the per-cohort exploration floor is never invoked. You're paying the complexity cost without the benefit, on exactly the "better than TikTok" differentiators.
- **Pagination is fragile at scale:** the candidate pool is page-independent (no offset/keyset), cross-page dedup rests on a fire-and-forget Redis write that a prefetch races, cold users literally can't paginate past page 1, and composeFeed can return short pages that prematurely end sessions.
- **Concurrency:** SessionState and UserProfile are read-modify-written with no locking from multiple concurrent goroutines, silently losing exactly the mood/dopamine/resistance signals the product is differentiated on (invisible to `go test -race` — it's a Redis-layer lost update).

Net: a strong engine carrying a layer of impressive-looking machinery that is partly inert, plus one hot-path DB cost that must be fixed before scale. The good news: most of the highest-impact fixes are small, and fixing them brings a large fraction of the currently-dead intent back online cheaply.

## 2. Top quick wins (highest impact-to-effort first)

1. **Cache `getContentScore` (request-scoped memo + short-TTL global cache).** The dominant feed-path DB cost: 3 queries/call × ~150-250 calls/request, all on ~100 IDs, re-fetched 2-4×. The idiomatic `SignalCache[T]` already exists and caches cheaper lookups; this one heavy function bypasses it. *(high / medium)* — `feed_engine.go:2067-2306` (def); call sites `3863, 3980, 4025, 4043, 4056`, `mmr.go:202`, `surprise_injection.go:102/123`, `explore_feed.go:132/179`, `candidate_sources.go:446`.

2. **Add buckets for `slotNostalgic` / `slotFavCreator` / `slotFreshBlood` in composeFeed.** These three slot types are never appended to any bucket, so the calming/nostalgic/creator_focus/fresh_blood strategies and the frustrated/bored mood patterns silently collapse to generic top-hook content — the opposite of "rebuild trust with proven favorites." The needed signals (`unseenBonus`, `social`, `interactedIDs`) already exist in `ScoreBreakdown`. *(high / small)* — `feed_engine.go:3347-3358`; patterns at `3180-3220, 3290-3326`.

3. **Over-fetch by one in `coldStartFeed` so `hasMore` can be true.** `battleLimit+shortLimit == limit` exactly and queries use `LIMIT $1` with no `+1`, so `hasMore := len(items) > limit` is structurally always false — brand-new users (the cohort you most need to retain) cannot paginate past page 1, and refresh re-serves the same shuffle. Mirror the existing `GetPostsPaginated` limit+1 pattern; add seen-dedup to the cold path. *(high / small)* — `feed_engine.go:3578-3628, 3645-3661`.

4. **Make the seen-set write synchronous before responding.** Pagination dedup relies entirely on the Redis seen-set, but it's written via `go markShownBatch` while the next page reads it synchronously — a page-2 prefetch can re-serve page-1 content. Inline the `ZADD` (cheap, one pipeline) and defer only trim/expire to the goroutine. *(medium / small)* — `feed_engine.go:4011` (writer), `3943` / `explore_feed.go:172` (reader).

5. **Fix the Platt calibrator train/serve skew.** Fit on raw logit `z` but queried on bounded `0.25*tanh(z)`, so `calibBonus` is pinned near `σ(B)` — a miscalibrated, mostly-bias term consuming its ±0.15 budget. Pass raw `z` to `plattCalibrate` at serve time (the per-creator residual path at `learning_to_rank.go:335` already does this correctly). *(medium / small)* — `feed_engine.go:2991-2996`, `learning_to_rank.go:121,162-164`, `calibration.go:58-79`.

6. **Wire `recordSessionMoodOutcome` into the session-end path.** It has zero callers, so the learned mood-transition graph is never written and `moodTransitionBonus` runs forever on hand-coded seed priors. One call from the `app_background`/`session_end` branch revives the documented learning loop (add a persistence/aggregation layer for multi-instance). *(medium / medium)* — `mood_transition.go:79-105, 181-202`; call from `feed_engine.go:803`.

7. **Make the MMR position-lambda ramp actually run on For You.** `applyMMRDefault` passes `λ=0.72`, which fails the ramp gate, so the entire fragile-attention head re-ranks at flat relevance-heavy λ instead of the intended 0.55→0.85 diversity ramp. Pass `λ=0` (or an explicit ramp boolean) from `applyMMRDefault` and drop the fragile `lambda == mmrLambdaHead` float-equality check. *(medium / small)* — `mmr.go:127-134, 200`.

8. **Fix engagement-latency weighting inverting positive labels.** `WatchDurationMs` is fed in as "impression-to-tap latency," so a full 15s watch (the strongest positive) gets the *minimum* 0.5× training weight, scaled inversely to video length. Gate the latency reweight to true tap events; pass `latencyMs=0` for view/complete. *(medium / small)* — `engagement_latency.go:38-84`, `feed_engine.go:849-858`, `learning_to_rank.go:306-312`.

9. **Push hard negatives into retrieval SQL.** No source excludes blocked creators / bounced content; they burn candidate budget then get scored to zero. The blocked set is already warmed before fetch — add `AND c.creator_id <> ALL($blocked)`. *(medium / small)* — `candidate_sources.go:107-139`, `signals_negative.go:209-215`. (Note: the user-facing block button writes `user_blocks` but never calls `MarkBlocked`, so cover both via a `user_blocks` join.)

10. **Compute `EnergyPreference` from real content `energy_level`, not the challenge-vs-post ratio.** Since the feed went challenge-only, `postViews≈0` pins it to ~0.8, degrading the 0.20-weight EnergyFit term into a uniform "prefer high-energy" bias. Mirror the `EnergyByHour` query that already reads real energy. *(medium / small)* — `feed_engine.go:1591-1605, 2420-2427`.

11. **Tokenize the energy classifier instead of substring `Contains`.** Short needles (`run`, `ski`, `code`, `game`) false-match `brunch`, `skincare`, `decode`. The repo already has a `tokenize()` helper (`challenge_validation.go:195`) to reuse. *(medium / small)* — `energy_classifier.go:359-366, 85-142`.

12. **Collapse `skipLatencyWeight` into `engagementLatencyWeight` (byte-identical duplicate), or give skips real constants.** Today editing one curve silently diverges intent from implementation. *(low / small)* — `engagement_latency.go:38-50 vs 57-69`.

13. **Make `negativeProfileMineEpoch` atomic.** Non-atomic `int64++` from concurrent goroutines is a data race that `go test -race` will flag once the diag reader is wired. *(low / small)* — `negative_profile_mining.go:195-205`, writer at `feed_engine.go:868`.

## 3. Bigger bets (high-impact, larger-effort), by theme

### Ranking quality

- **Make embedding retrieval a true ANN retriever.** `sourceEmbeddingNeighbors` cosine-reranks the *recency pool* (`fetchCandidates(limit*10)`), so it can never surface semantically-similar *older* content — the whole point of embedding retrieval — and overlaps ~100% with the recency lane. Store content vectors in pgvector (`candidate_sources.go:475-478` already reserves the symbol) and do `ORDER BY embedding <=> $userVec LIMIT k`. Also unify retrieval and ranking on the *same* content vector: retrieval uses the hash-trick prior while ranking uses the trained vector, so the two stages optimize inconsistent objectives. — `candidate_sources.go:423-473`.
- **Tame the additive-bonus stack so the cohort-weighted mood/energy core isn't drowned.** ~20 un-cohort-weighted bonuses (battleBoost +0.50, variableReward +0.28, reentry +0.25, momentum +0.32, …) sum well past +3.0 over a base of ~1.0-1.2. `variableReward` alone exceeds the entire EnergyFit term the design calls its "unique advantage." Group terms into named buckets with per-bucket caps and route retention/exploration bonuses through cohort weights so at_risk/cold cohorts aren't dominated by jackpot noise. — `feed_engine.go:2577-2586` vs `2968-3018`.
- **Make the Bayesian uncertainty bonus real (or relabel it).** It ignores the candidate score it claims to modulate and injects fixed-scale per-cohort Gaussian noise (±0.10, larger than EnergyFit's max) — and because it tracks Bernoulli label variance with no `1/√N` term, it never shrinks with data (it degenerates to a near-uniform ±0.10 coin-flip on every item, forever). Scale by `4·p·(1-p)` / the SE of the mean, or demote to a small fixed exploration epsilon. The repo's `bandit.go` Beta posterior already shows the correct shrinking-variance pattern. Also stop re-seeding `rand` per candidate; thread one `*rand.Rand` per request. — `bayesian_ltr.go:51-88, 141-168`.
- **Fix the bandit's censored, loss-biased training and wire up the dead exploration machinery.** `updateArm` only runs on the rare resistance-driven mid-session switch, so the bandit never credits a strategy the user stayed on. Separately, the entire `softMix`/`cohortExplorationFloor` family is referenced only by tests — the documented per-cohort exploration floors have zero runtime effect (a lying "production scoring" comment). Credit the in-flight strategy at session boundaries and either wire `softMixForCohort` into the ranker or delete it and fix the comment. — `feed_engine.go:991-999, 1035-1071`; `bandit.go:139-281`, `feed_engine.go:1271`.
- **Run anti-loop detection *before* scoring.** `detectLoop` runs after scoring + MMR, and its override is only honored by `getFeedPattern` when `ResistanceLevel >= 2` — so category-monoculture / creator-flood / dopamine-collapse loops (which fire at RL 0-1) only get fixed on the *next* page, defeating the 30-sec-vs-30-min retention goal. Move detection before the scoring loop. — `feed_engine.go:3865, 3947, 3952-3958`.
- **Fix `RecentWins`/`RecentLosses` conflating votes-received with battle outcomes.** Any active responder is classified "winning," so the loss-recovery ego-repair logic almost never fires for the users it targets; the bias also propagates into `CategoryByEgo`. Derive win/loss from actual per-challenge vote-share. — `feed_engine.go:1609-1625`.

### Scale & latency

- **`getContentScore` is the marquee item (see quick win #1)** — caching it is the single highest-leverage scale change. In addition, **bound its all-time `feed_events` aggregate** to a rolling window or serve it from a precomputed per-content stats row; today a viral item re-aggregates millions of rows per candidate per request, while the adjacent trending query is correctly 2h-bounded. — `feed_engine.go:2081-2098`.
- **Denormalize challenge `likes_count` / `response_count`.** Every candidate query `LEFT JOIN (SELECT challenge_id, COUNT(*) … FROM challenge_likes GROUP BY challenge_id)` with no time bound, so each feed request aggregates the all-time likes table 5+ times (Postgres can't push the outer window/LIMIT into the uncorrelated subquery). Maintain counts via triggers / the like/respond handlers. The biggest retrieval-path bottleneck. — `candidate_sources.go:262-263, 322-323, 383-384`; `feed_engine.go:4780-4781`.
- **Cache `UserProfile` and move the stale recompute off the hot path.** Every feed request hits Postgres for the profile (no cache despite the idiomatic `SignalCache`), and a stale (>5min) profile triggers ~26 sequential queries *inside* the handler before any candidate is scored, with no singleflight (thundering-herd risk). Add `SignalCache[*UserProfile]` + a singleflight-guarded background recompute that serves the stale profile immediately. — `feed_engine.go:1311-1323, 1404-1434, 1945-1989`.
- **Make candidate retrieval page-aware (keyset/offset).** The pool is fixed at `pageSize*5` for every page with no offset, so deep sessions exhaust the deterministic top-N and `filterUnseenScored` re-admits seen items — engaged users get re-watches mid-session even though fresh catalog exists (worse at scale, not better). Wire `page` into the existing `*Windowed` variants or scale `candidateLimit` with page. Also add a top-up pass + decouple `hasMore` from composed length so short pages don't prematurely end pagination. — `feed_engine.go:3845-3851, 3943, 4074`; `seen_filter.go:147-188`.
- **Shard / batch the impression aggregator.** Every 5 min it cursor-SCANs the whole keyspace then does serial per-user `loadUserProfile`+`saveUserProfile` round-trips — O(users) serial DB calls in one goroutine, which can't finish within the tick at scale. Use a bounded worker pool + batched `WHERE user_id = ANY($1)` + multi-row UPSERT + per-tick cap with cursor resume. — `impression_aggregator.go:220-252, 256-314`.
- **(Lower) Wire per-creator impression-bounce stats into ranking, or stop computing them.** `getImpressionStats` builds a full `byCreator` map that only the admin endpoint reads; mirror the category `impressionBouncePenalty`. — `impression_aggregator.go:144-194`.

### Correctness

- **Serialize SessionState read-modify-write.** Plain Redis GET/SET from four concurrent paths (event handler, batch handler, impression goroutine, inline feed handler) on the same `session:<uid>:<sid>` key — last SET wins, silently dropping `ItemsSeen`/`SkipStreak`/`DopamineBudget`/`BounceStreak`, the exact inputs to resistance/mood/strategy detection (biasing toward "engaged"). Use HINCRBY for pure counters and a WATCH/MULTI or Lua step for the struct. The codebase already uses HIncrBy/TxPipeline elsewhere. — `feed_engine.go:528-570, 793-1003`; `impression_aggregator.go:95-116`.
- **Serialize UserProfile writes.** Multiple fire-and-forget goroutines (negative-feedback miner, `recordStrategyOutcome`, the impression aggregator, `computeUserProfile`) each do `load → mutate → saveUserProfile(full 28-column row)`, clobbering each other's region. The fix pattern already exists (`creator_residual.go:68-72` sync.Map of per-key mutexes) and `persistSessionLength` already documents the hazard and avoids the full save. Use a per-userID mutex or field-scoped UPDATEs; also correct the stale `negative_profile_mining.go:160-177` comment. — `feed_engine.go:864-871, 1035-1071, 1945-1989`.
- **Inject the surprise wildcard after composeFeed.** It's inserted into `scored` then `composeFeed` re-buckets from scratch, discarding its position; with no `ScoreBreakdown` it can't match the `slotSurprise` criteria and only ever lands in the hook bucket — so the filter-bubble defense is largely a no-op on For You (it works correctly in `explore_feed.go`). Inject post-compose like `injectSuggestedAccountsCard`. — `feed_engine.go:3996-4000, 3345-3420`.
- **Move hour-of-day routing to user-local time.** Both build (`EXTRACT(HOUR FROM created_at)` in UTC) and read (`time.Now()`) sides use server time with no per-user timezone, so "morning commute / late-night" buckets are wrong for everyone outside the server TZ. Capture a client UTC offset and bucket by user-local hour. (Lower urgency: the live effect is two small bounded priors; the dramatic strategy-mix routing is currently dead code.) — `hour_routing.go:41-173`, `feed_engine.go:1685-1697, 2695-2697`.
- **Unify the cold→warm handoff.** `coldStartThreshold=15` gates the cold feed but `bootstrapColdEventThreshold=20` gates the bootstrap mix, so `applyBootstrapMixIfCold` only ever runs for events in [15,19], the documented 0.50 bootstrap mix at 0 events is unreachable dead intent, and users hit a hard cliff from 100% popularity to personalized scoring at exactly 15 events. Feed the Wilson bootstrap pool into `coldStartFeed` and decay the mix continuously. — `bootstrap_cold_start.go:39-61, 213-217`.

## 4. Per-subsystem one-liner

- **Core scoring & weight blending** — Thoughtful, well-clamped base; but two ML heads are silently broken and un-cohort-weighted bonuses drown the mood/energy core. *(4 findings)*
- **Pipeline orchestration** — Stage ordering is sound; pagination correctness rests on page-independent retrieval + a racy fire-and-forget seen-write, and surprise injection is discarded by bucketing. *(5)*
- **Session state & psychology** — Rich, mostly-correct plumbing, but three slot types have no buckets and the learned mood model is never written, neutralizing large parts of the psychology layer. *(4)*
- **User profiling & cold start** — Strong design (cohorts, Wilson bootstrap, widening tiers), undercut by an uncached 26-query recompute, a collapsed EnergyPreference, and cold users who can't paginate. *(5)*
- **Candidate generation & sources** — Architecturally excellent (7 fail-open sources, real-time trending), bottlenecked by all-time likes GROUP BY, a fake embedding "retriever," and no negative-signal pushdown. *(5)*
- **Learning-to-rank & calibration** — Competent online SGD with good label hygiene and IPW; the calibration/uncertainty layers stacked on top are train/serve-skewed and never persisted. *(3)*
- **Embeddings & two-tower** — Solid design with proven cache equivalence; hot-path recompute, retrieval/ranking vector mismatch, and minor recency double-counting drag it down. *(5)*
- **Exploration (bandit/anti-loop/MMR/surprise)** — Algorithms are correct but the wiring is hollow: bandit trains on a censored loss sample, the lambda ramp and exploration floor are dead code. *(4)*
- **Negative signals & seen filter** — Well-designed TTL/trim/min-keep capture; undermined by a racy profile write and a fire-and-forget seen-set that duplicates pages. *(4)*
- **Engagement quality & context signals** — Engagement-quality and watch-ratio heads are excellent; latency weighting inverts positive labels and hour routing ignores user timezone. *(4)*
- **Scale, latency & hot-path cost** — Per-user warm-once design is genuinely good; the single uncached `getContentScore` undoes much of it. *(2)*
- **Correctness, concurrency & data integrity** — Resilient and injection-free with mutex-guarded model state; the unlocked SessionState/UserProfile RMW paths and uncached `getContentScore` are the real gaps. *(4)*

## 5. What's already strong (do NOT touch)

- **Per-user warm-once caching.** `warmUserSignalCaches`/`warmPrecomputedSignals`/`warmNegativeSignals` collapse ~5 lookups × 100 candidates into a handful of queries; `populateTopResponses/CommentCounts/HLSManifestURLs` batch with a single `IN(...)` per page. This pattern is correct — replicate it for `getContentScore`, don't disturb it.
- **Fail-open candidate generation.** Parallel sources via `sync.WaitGroup`, per-source `recover()`, per-source nil-degrade, and a legacy single-path safety net when all sources return empty. Concurrency-correct and resilient.
- **Real-time trending (`trending_realtime.go`).** O(1) `ZIncrBy` writes, decay in a bounded pruner, user-engagement-quality weighting for anti-bot, negative weights for reports/skips. The right shape.
- **Cohort classifier + per-feature weight tables (`cohort.go`).** Cheap request-time personalization with sensible per-cohort shapes and a safe Engaged default; consumed by both source blending and scoring.
- **Online LTR hygiene.** Decaying LR, sparse L2 decay, bounded tanh delta (±0.25), warmup gating, IPW position-propensity (clamped 1/propensity), snapshot-then-flush, and genuinely no label leakage (outcome-ish features come from historical caches known at serve time). The watch-ratio head is correctly separated (length-normalized label, trained only on valid ratios). Per-cohort source blending (`cohort_source_blending.go`) is similarly well-guarded (min-weight floor, clamped exponent, renormalization, slow EMA).
- **Embedding stable/dynamic split** with a test pinning `cached == fresh` equivalence, plus principled cold-start sentinels gating the cosine bonus and neighbor source; bounded creator-residual calibration with per-creator mutex.
- **`session_diversity.go`.** Superlinear `(n-1)²` penalty, bulk `HGETALL` hydration, Redis-TTL-scoped to the session, no double-counting — correct and scale-aware.
- **Negative-signal tiering & seen-filter min-keep.** Blocked = hard zero, unfollow = decaying soft penalty; TTL'd/trimmed ZSETs with consistent `post:`/`challenge:` namespacing; the `seenFilterMinKeep=8` re-admit floor is a thoughtful product-aware "never show a blank page" guarantee.
- **`engagement_quality.go` + `watch_ratio.go`.** Spam-resistant trust multiplier with neutral fallback and correct blast radius (trending only, not per-user state); watch-ratio label correctly normalized by video length with per-cohort warmup and bounded bonus.
- **General robustness.** Uniform parameterized SQL (injection-free), consistent `rdb` nil-guards that fail open, all long-lived in-memory model state mutex-guarded, and `persistSessionLength`'s deliberate field-scoped UPDATE + SETNX idempotency — the correct pattern the other profile writers should copy.
- **Bandit core math.** Marsaglia-Tsang gamma sampler with the shape<1 trick, Beta via two gammas, softmax with max-subtraction/clamping, lazy time-decay toward the (1,1) prior, and an observation cap — the algorithm itself is correct; only its wiring is the problem.
